# Chift × Horus, Part 1: critical review register (internal)

> **Internal only. Not for Chift.** A senior-BA challenge of the Part 1 solution, used to revise the mappings, the notes and the external report. Companion to `02_interview_prep_guide.md`.
>
> **Note:** the corrections were applied to the source data and the notes. The detailed HTML reference (`chift_horus_mapping_report.html`) was then deliberately kept unchanged; the concise report `chift_horus_connector_assessment.html` follows the corrected positions and lists the material corrections in its appendix B.

## How the review was done

- Eleven independent reviewers each took one lens: case requirements, Chift contract fit for read routes, Chift contract fit for write routes, the three Task B mappings row by row, a Horus fact-check, business rules, integration edge cases, the Chift interviewer's view, and internal consistency.
- A separate verifier then tried to refute every finding against the sources: quotes re-checked, the solution searched for an existing answer, and outside knowledge excluded. 114 findings survived and 2 were refuted (see the end of this file).
- The 114 findings were merged into **63 issues** (3 critical, 39 major, 21 minor), and each was turned into precise edits to the mapping data, the report text, the working assumptions and the notes.
- Sources were the same as before: the case, the Chift OpenAPI (SDK 0.6.16), the Horus API reference and guides, plus **one new Horus source found during the review: the two tax-combination spreadsheets** linked from the invoice endpoints (`appendix_horus_tax_combinations.md`).

### Critical issues

#### S1-01. Verdict scale not applied as printed: analytic plans rated Supported despite emulated paging and hidden Free dimensions

- **Category:** Inconsistency · **Routes:** Analytic plans retrieval, Accounting folders retrieval, All (headline split) · **Lead decision:** LD1
- **Why it matters:** The 2 Supported / 9 workaround split is the first number Chift sees. Under the report's own printed definition, analytic plans is a workaround. The exception exists only in internal D11 and in data/analytics.json ('slicing at most 8 rows is trivial'), so a reviewer who applies the scale gets a different headline, and that casts doubt on every other verdict.
- **Correction:** LD1 wins over the 'Option A' (qualify the Supported definition) that both findings recommend: there are no exceptions by decree. Print the LD1 definitions in section 2. Rate analytic plans 'Supported with workaround' with Low complexity, for two reasons. First, Chift Get Analytic Plans is paginated (appendix_chift_spec_extract.md › GET analytic-plans: 'param[query] page: integer default=1', '-> ChiftPage_AnalyticPlanItem_'), while cost-schemas.list has no paging, so page/size/total are emulated. Second, Free-type schemas are not exposed in v1 pending C9. That is a design choice, not a Horus gap: cost-schemas.list returns them ('`900`: Free'). Folders stays Supported only because the Chift folders route is unpaginated ('-> array[FolderItem]') and because this revision stops calling folders.info per folder by default for addresses[].country (LD1: 'country via folders.info only if Chift needs it'). The generator computes the new split (expected 1 Supported / 10 workaround / 0 not supported). No prose or notes may keep '2 / 9' or 'two map almost directly'.
- **Input needed:** Chift: Helpful · Horus: Not needed
- **Ask Chift:** Should Get analytic plans list Horus Free-type dimensions (they have no enumerable analytic accounts and are not accepted on write in v1), or hide them as proposed (C9)? Is the folder address country needed on Get folders, given that it costs one extra Horus call per folder?
- **If Chift raises it:** Say: 'We applied one scale strictly. Anything that emulates Chift paging or hides a capability is a workaround, even when it's trivial.' Analytic plans is a low-complexity workaround: at most 8 rows sliced in memory, and Free dimensions hidden by choice, pending C9. Folders is the only route Horus serves natively.
- **Revised in:** internal notes, mapping data, report text, working assumptions (done)

#### S2-01. VAT catalogue must follow the now-available tax-combination files per legislation and direction; Luxembourg codes break the current D2 grammar and enum validation

- **Category:** Unsupported conclusion · **Routes:** Invoice creation, Invoice retrieval, VAT codes (dependency) · **Lead decision:** LD7
- **Why it matters:** VAT is the report's headline risk, and the Chift team can open the two spreadsheets linked from the Horus invoice pages. As written, the mapping validates TaxOrigin against the reference enums and allows a country only on origin 13. It would therefore reject or mislabel valid Luxembourg lines, and it serves the same VAT-code list to every folder. It also labels 'no VAT-code entity' as documented, although ledger lines return a VatCode on read, which invites an easy challenge.
- **Correction:** LD7 governs. (1) Build the D2 catalogue from appendix_horus_tax_combinations.md, one list per folder Legislation (BE/LU, read from folders.info) and direction (sales list for customer_*, purchase list for supplier_*): sales BE 18 rows, LU 58; purchases BE 109, LU 146. A tax_code is valid only if it is in the folder's list for the invoice direction (otherwise 422). GET vat-codes is folder-scoped, and get_invoices encodes against the same list. Cache Legislation and IsVatLiable from folders.info. (2) Keep the D2 id shape, but the country component applies to every OSS row: BE origin 13, and LU origins 24, 26 and 29, where the files give rate and country as 'XX', meaning they are supplied per transaction. On LU purchase rows with TaxCondition 0 (COUNTRY), the TaxConditionValue is the country code ('XX (= CountryCode)'). These rows are templates: on write, any EU country code and rate is accepted. Which concrete OSS codes GET vat-codes lists is a proposal for Chift (C2). (3) New documentation discrepancies, all facts from comparing the reference with the files: (a) invoices.sales.new has a TaxOrigin enum of 0–20, but the LU sales file uses origins up to 35, and codes 15, 16, 18, 19 and 20 carry different labels (e.g. 20 = 'Prestations hors Luxembourg' in the reference vs 'UE - Prestation de services - exo pays acheteur' in the file); (b) invoices.purchases.new has an enum of 0–39, but the LU purchase file uses 40–56, and BE codes 12, 16, 22, 23 and 27 carry different labels (e.g. 12 'Hors CEE sans facture' vs 'Achat TVA Marge'). So validate against the files and never against the reference enums, take catalogue labels from the files, and ask Horus which source is authoritative. Also flag the LD7 discrepancies: TaxCountryCode is described as 'only for TaxOrigin = 13'; PCT appears as 35/50/75/85 in the combinations but as 0.35… in 'Available values'; and the 'Nationam' typo. (4) Qualify 'no VAT-code entity' as LD7 requires: there is no VAT-code list endpoint and no VAT code on write. On read, VatDetail.VatCode and VatHeading (account-histories.list/.info, customers/suppliers.outstanding) are strings whose meaning is undocumented. D2 stays the v1 design. Ask whether VatCode is stable and maps one-to-one to a combination, TaxKind included: if so, the purchase tax_code = null on read could be removed. (5) Folders with IsVatLiable=false: the files have no variant for them, and the combination such a folder expects is undocumented. Add an edge case and an H1 sub-question.
- **Input needed:** Chift: Helpful · Horus: Required
- **Ask Chift:** Should GET vat-codes return each folder's own list (Belgian or Luxembourg, sales and purchases)? For OSS rows, whose rate and country vary per sale, should the list contain only the destination countries a consumer asks for?
- **Ask Horus:** Are the two tax-combination spreadsheets current and complete for BE and LU, and how are changes announced? The LU files use TaxOrigin codes outside the invoices.sales.new (0–20) and invoices.purchases.new (0–39) enums, and several codes carry different labels in the reference and in the files (e.g. sales 20, purchases 12): which source is authoritative, and does the API accept the LU codes? Is TaxCountryCode used for the LU OSS origins 24, 26 and 29? Is the PCT value sent as 35 or 0.35? Which combination must a folder with IsVatLiable=false send? How is an invalid combination rejected (ErrorType)? What do VatDetail.VatCode and VatHeading represent, and are they stable and one-to-one with a combination (TaxKind included)?
- **If Chift raises it:** Say it plainly: the spreadsheets were not in the first document set. They were downloaded on 13 Oct 2026 from the links on the invoice pages, and the catalogue is now built from them, per legislation and direction. Show the BE sales sheet in appendix C: it matches the reference exactly. Present the LU code differences and five BE purchase labels as a documentation question for Horus, not as a blocker.

#### S3-01. Foreign-currency miscellaneous operations are rejected, although Chift's contract says to convert them at the supplied rate; the balance is also checked on amounts other than those sent

- **Category:** Overlooked requirement · **Routes:** Create miscellaneous operation, Get journals · **Lead decision:** LD6
- **Why it matters:** The solution rejects every non-EUR operation and accepts the rate only as 1 or null. Chift's contract makes the rate mandatory for exactly this case and describes conversion for journals that do not allow other currencies. The solution itself returns other_currencies_allowed=false for Type 600 journals. The rejection contradicts Chift's own text, drives a headline data-loss claim and a verdict reason, and would block clients who occasionally book foreign-currency entries. Separately, the connector checks the balance on rounded amounts but sends unrounded ones. That produces false 422s or Horus 400s, and the gap matters more once amounts are converted.
- **Correction:** LD6 governs. Fact (D): the misc-op body has no currency or rate field ('Debit *: number // Non-negative amount', no CurrencyCode), so Horus stores the amounts in the folder currency (EUR assumed, D4/H4). New rule (proposal): currency = 'EUR' → amounts are sent as given. Currency ≠ 'EUR' → the operation is converted at the supplied rate; it is never rejected and never posted unconverted. currency_exchange_rate is then required. Null, ≤ 0 or exactly 1 → 422, because 1 is the Chift default and cannot be told apart from a missing rate. Who converts is a question for Chift. Preferred reading of 'an exchange rate must be provided for Chift to convert the amounts to the journal currency': Chift core converts before calling the connector. Fallback: the connector converts each line at the supplied rate, with the rate direction set by Chift. Every amount is normalised once (converted if needed, then rounded to 2 decimals). The same normalised values feed the balance check, Debit/Credit and CostLines.Amount. If they do not balance → 422, unless Chift defines a residue rule. Two examples: 10.004 and −10.001 pass a rounded check but are sent unbalanced; 33.333 + 33.333 − 66.666 balances as sent but fails after rounding. The original currency is not kept in Horus (it may optionally be noted in the line comment). The response never pairs EUR amounts with a foreign code (D4): it echoes the request currency, rate and amounts when lines are echoed, and returns 'EUR' with rate 1 when lines are rebuilt from the read-back; Chift makes the final call. Replace 'EUR-only' everywhere with: 'stored in EUR; foreign-currency operations are converted at the supplied rate and the original currency is not kept'. Remove 'non-EUR operations' from C3, because 'ignore with a warning' would post foreign amounts as EUR. Get journals' other_currencies_allowed=false on Type 600 then matches the write rule. The route's verdict texts (summary, verdict_rationale, one-liners, card brief, D11) are rewritten in issue S3-05 using this wording.
- **Input needed:** Chift: Required · Horus: Helpful
- **Ask Chift:** When an operation arrives in a currency other than EUR with currency_exchange_rate, does Chift core convert the amounts before calling the connector (as other_currencies_allowed=false suggests: 'for Chift to convert the amounts'), or must the connector convert? In which direction is the rate expressed? How should a rounding residue on a balanced operation be absorbed? Should the response echo the original currency and rate, or EUR with rate 1? Does Chift core round amounts before calling the connector?
- **Ask Horus:** Is the folder base currency always EUR (BE/LU legislations)? How many decimals do Debit/Credit accept on book-entries.miscellaneous-operations.new, and is the balance checked on exact values?
- **If Chift raises it:** Horus stores miscellaneous operations only in the folder currency. Chift's own contract tells the connector what to do in that case: convert at the supplied rate. So the only real loss is the original currency, not the operation. Open by asking whether Chift core already converts before calling connectors; if it does, the connector only checks the balance on the converted amounts.
- **Revised in:** internal notes, mapping data, report text, working assumptions (done/partial)
