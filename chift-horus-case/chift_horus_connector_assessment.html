Chift product/tech case · Part 1 · Mapping Chift – Horus

Horus connector assessment

Can Chift's accounting routes be served from the Horus Software API, which Horus endpoints would each route use, how the requested attributes map, and what must be confirmed before building.

Prepared by Silas Deblanc For Chift, Product & Tech Date 13 October 2026 Status For discussion Basis desk analysis of the documentation, no live API calls Detailed reference full technical mapping (unchanged; corrections in appendix B)

1Executive summary and feasibility

The Horus Software API has a documented endpoint for the core object of every Chift route in scope, so the documentation rules out none of the 11 routes. That is not the same as every route being settled. Three routes are confirmed by the documentation (ledger account creation, analytic plans and analytic accounts). Four are feasible but rely on assumptions the documentation does not confirm (client creation, journals, chart of accounts and folders). Four need answers from Horus or decisions from Chift before their design is final (invoice retrieval, invoice creation, miscellaneous operations and outstanding items); these carry most of the business value and most of the effort. Behaviour on large folders cannot be concluded from the documentation for any list route.

How sure are we?

What the documentation confirms

  • Every object in scope has a documented Horus endpoint for the operation the case needs: companies.new/info/list (clients); invoices.sales.new and invoices.purchases.new, optionally with the PDF (invoice creation); book-entries.list and account-histories.list (invoice retrieval); daybooks.list (journals); accounts.new and accounts.list (ledger accounts, chart of accounts); folders.list (folders); book-entries.miscellaneous-operations.new (miscellaneous operations); cost-schemas.list and cost-sections.list (analytics); customers.outstanding, suppliers.outstanding and invoices.sales.outstanding.list (outstanding items). Documented
  • What is established is feasibility at capability level. No route lacks a Horus capability in the documentation reviewed, so the reference's headline holds only with the qualifier 'blocked by a missing capability in the documentation reviewed'. Applying the verdict definitions strictly gives 1 Supported route (folders) and 10 Supported with workaround. On current evidence, the open questions can degrade behaviour or narrow scope (Luxembourg VAT codes, direct posting, large folders) but do not remove a route. Derived
  • The write-side rules are documented, so the connector can check them before posting. Invoice total = base + tax, and the lines add up to the header. Cost lines add up to the line base amount. Miscellaneous operations must balance. Type 0/1 marks invoice or credit note. Confirmed is false by default, Number may be 0 only while unconfirmed, and AutoGenerateNumber works only on confirmed operations. Documented
  • The accepted VAT combinations are published in two spreadsheets linked from the invoice reference pages, downloaded 13 Oct 2026: sales 18 BE and 58 LU rows, purchases 109 BE and 146 LU rows. folders.list returns each folder's legislation (BE/LU), so a per-folder catalogue can be built. Documented
  • Client open items are native. invoices.sales.outstanding.list returns a folder's open sales invoices and credit notes with OpenAmount, PaymentStatus and TransactionType, and can be filtered by company. Documented
  • The connection mechanics are documented: an OAuth authorisation code flow with one license per grant, an api_url per license, one-hour access tokens and single-use refresh tokens. ModifiedAfter exists on companies.list, book-entries.list and account-histories.list, and updated invoices and operations get a new Id. Documented

What depends on an assumption

  • Emulated paging, totals and day-level filters are correct only if Horus lists return complete result sets for a folder and period. This is deduced from the absence of paging parameters and is unverified on large folders. Derived
  • Invoice/credit-note classification on read is a proposed rule, not documented behaviour: the daybook type decides, and the partner-line sign is used only in folders without a credit-note daybook. Assumption
  • Ledger amounts on read are in the folder currency (EUR). Open sales items returning TotalAmount next to TotalCurrencyAmount suggest this, but no source states it. Assumption
  • Supplier outstanding items: suppliers.outstanding without CompanyIds returns every supplier, and partially matched lines are either returned or covered by a fallback read of the supplier accounts. Assumption
  • The spreadsheets are current and complete, and the API accepts the Luxembourg TaxOrigin codes that the reference enums omit. Assumption
  • Analytic combinations are derived as the product of independent per-plan percentages, with largest-remainder rounding. Assumption
  • Field meanings used in the mapping are assumed. active = NOT CustomerActivitySuspended. The invoice header Comment carries reference and customer_memo and comes back on read in the partner-line comment or a remark field (D3). Assumption

What needs confirmation from Horus or Chift

  • Horus, VAT: the spreadsheets are current and complete, which origin list is authoritative, the combination for folders that are not VAT liable, and how an invalid combination is rejected (H1). To confirm
  • Horus, posting: whether a credit note may sit in a sales or purchase daybook and whether the type can be read (H2); duplicate-number behaviour, commits after a timeout and numbering of confirmed invoices (H3); whether every licence and user may confirm entries (H21). To confirm
  • Horus, reads: the currency of ledger amounts and the direction of CurrencyRate (H4); rate, size and time limits (H5); completeness and partial matching of the outstanding endpoints (H8). To confirm
  • Horus, onboarding: which documentation is authoritative (the case links the former apiary documentation), integration registration, the authorising user, and a test license or folder (H17 and new questions). To confirm
  • Chift, architecture: the posting mode and the rule for invoices without a number (C1, C7), caching between page calls and request timeouts (C14), and who converts foreign-currency operations (C15). To confirm
  • Chift, Task B conventions: input and output signs (C5), acceptance of a synthetic VAT catalogue and the VAT-amount policy (C2), and partner-code generation and the meaning of partner_info (C8). Also needed: confirmation that the contract used (OpenAPI bundled in the chift 0.6.16 SDK) matches docs.chift.eu. To confirm

What cannot be concluded yet

  • Whether the routes perform and stay correct on large accounting-firm folders. No limits are documented and no volume test has been run, so the reference's claim that the connector 'can absorb' the workarounds is not established. To confirm
  • Whether supplier outstanding items are complete for partially paid invoices. This depends on H8, or on the fallback being validated on test data. To confirm
  • Whether Chift's 'posted' can be delivered on every connection. Confirmation rights are undocumented (H21); if confirmation is restricted, entries come back as drafts. To confirm
  • Whether every VAT case clients need can be expressed. The files have no variant for folders that are not VAT liable, Luxembourg uses origins outside the reference enums, and the format of the PCT value is ambiguous. To confirm
  • Whether incremental synchronisation is complete. It is undocumented whether matching changes or accountant edits update ModifiedAfter, and whether an edit in Horus Office creates a new Id; no deletion signal is documented (H10). To confirm
  • Whether the mapping holds for the API version the case links (apiary) and for the live Chift contract. The analysis used docs.horus-software.be and the SDK-bundled Chift spec, and sent no request to a Horus license or a Chift environment. To confirm

Key messages

  • One Chift call often means several Horus calls. Horus needs its own references (journal, partner, account and analytic codes), and a create returns only an id. The connector therefore looks up reference data, cached per folder, and reads records back. Horus has no endpoint that lists invoices, so invoice retrieval is rebuilt from ledger data.
  • VAT is the main mapping gap. Horus accepts no VAT code, only a combination of rate, origin and type (plus kind and condition for purchases), from lists Horus publishes per country and direction. Chift’s tax_code needs a translation table: a proposal Chift must accept and Horus must confirm.
  • Some Chift data has no place in Horus. Examples: line quantity and unit price, several addresses, person names, withholding tax, payment terms, and the account type. Chift must decide whether such inputs are rejected or dropped, and its clients need to know.
  • Accountant review is built into Horus. Entries pushed through the API are unconfirmed by default, and invoices cannot be deleted through the API. Whether Chift’s "posted" should bypass that review is a Chift decision. Proposal: review by default.
  • Two read-side points rest on undocumented behaviour: telling invoices from credit notes when reading entries, and computing supplier open amounts when invoices are partly paid. Both need confirmation from Horus.
RecommendationProceed to a short validation phase rather than a full build. First get a test licence and answers to the "before build" questions in section 6. Then build the reference routes and the simple creates, followed by invoice creation and miscellaneous operations. Leave the ledger-based reads (invoice retrieval, outstanding items) until Horus has confirmed credit notes, currency, partial matching and volumes. This is a proposal for Chift’s decision, not a commitment on behalf of Chift or Horus.

2How Horus differs from Chift

Chift exposes one standard accounting model; Horus has its own vocabulary and rules. The connector sits in between: it translates each Chift request into one or more Horus calls, converts fields, looks up Horus references, and assembles the response. Most of the effort and most of the risk come from the differences below, not from missing objects.

Chift route

One standard request, e.g. POST /accounting/invoices/multi-analytic-plans

→

Horus connector

  • translate fields and codes (VAT, signs, dates)
  • look up Horus references (journal, partner, accounts, analytics)
  • call Horus, combine the results
→

Horus API (one licence, one folder)

  • reference data, cached per folder
  • the create or list call itself
  • a read-back, because creates return only an id

Client creationFeasible with assumptionsCreation, read-back and merge are documented; only the search-key format, a few field meanings and the duplicate policy rest on assumptions or Chift decisions, and none blocks the build.

Horus endpoints

  • POST /companies.new main
  • GET /companies.info (read back created client)
  • POST /ibans.list (read back bank accounts)
  • POST /accounts.list (receivable account check, cached)
  • POST /companies.list (duplicate and free-code checks)
  • POST /companies.update (force_merge: supplier becomes customer)
  • POST /ibans.new (force_merge: add IBANs)
  • GET /folders.info (default language and country, cached)
  • POST /countries.list (country code check, cached)

What the documentation confirms

companies.new creates the company in a folder and requires FolderId, SearchKey, Name, IsCustomer, IsSupplier, IsVatLiable, LanguageCode and CountryCode (guide: Managing customers & suppliers). One call carries name, VAT number, one address, phone, website, emails, external reference, IBANs and the receivable (concentration) account. Create calls return only the new id (guide: Responses & errors); companies.info and ibans.list return the stored data. One company can be customer and supplier at once, and companies.update is a partial update, so force_merge maps to setting IsCustomer on the existing supplier. A VAT number already used by another company is refused by default, and search keys are unique within the folder.

Specificities to be aware of

  • A Horus 'company' is a customer or supplier inside a folder, not Chift's company or folder. One record carries both roles, which is why force_merge applies. Documented
  • Horus requires a search key, the third-party code accountants see, that Chift does not send. The connector must generate it per folder; deriving it from the name is a Proposal (C8). Assumption
  • A VAT number already used by another company is refused by default. A client that already exists as a supplier must go through force_merge, not a second record. Documented
  • Creation returns only an id (documented), so the response needs two to three extra read calls: company details, IBANs, and the receivable account unless cached. Derived
  • There is no idempotency key and no company delete endpoint. A blind retry can leave an undeletable duplicate, so the connector searches before retrying. Derived

What Horus cannot provide

  • One address per company: extra invoice or delivery addresses are lost, and later reads return one 'main' address.
  • No field for mobile, internal_notes, first_name, last_name, function or company_id; currency is read-only. These values are dropped and returned as null.
  • No company/individual flag: a client sent with is_company=false comes back as a company.
  • The enterprise number of a VAT-liable client has no separate field and is lost.
  • Non-IBAN bank accounts (local account number with routing code) cannot be stored.

Depends on an assumption

  • The search key (third-party code) is generated from the client name, numeric suffix on collision (Proposal, C8); Horus length and character rules are undocumented.
  • Required Horus fields Chift may not send are filled by rule: VAT liability from vat; language and country from folder defaults when missing (Proposal).
  • active=false is written as CustomerActivitySuspended=true, a field whose meaning is undocumented.
  • company_number of a non-VAT-liable client is stored as VatNumber with IsVatLiable=false; no documented write field exists for the enterprise number.
  • Phone and website written as PhoneNumber and Website come back as ContactPhone and ContactWebsite (pairing deduced from field names).
  • Duplicate protection rests on a pre-check by VAT number and external reference (Proposal); Horus documents no idempotency key.

Needs confirmation

  • Horus: search-key rules (maximum length, characters, case) and the error returned for a duplicate key (H7, H6).
  • Horus: meaning of CustomerActivitySuspended, Address2 and ContactPerson; how an enterprise number is written; default receivable account (H11).
  • Horus: is the duplicate-VAT check per folder, and does it ignore spaces and dots in VAT numbers (H25)?
  • Chift: search-key convention for new clients, and behaviour on a duplicate or a same-name client without VAT number (C8, C6).
  • Chift: force_merge policy (fill empty supplier fields or overwrite; conflicting external reference) (C6).
  • Chift: which address is kept when several are sent, and whether unstorable fields are rejected or dropped (C3).

Not yet concluded

  • Whether a create that timed out can still be committed later; until known, the check before a retry is best effort only (H3).
  • Whether sideloading on companies.list can return IBANs and the receivable account, cutting the read-back to one call (include paths undocumented, H15).
Invoice retrieval (multiple plans)Needs confirmationAll core invoice data is readable, but the invoice/credit-note split, foreign-currency amounts and large-folder behaviour rest on points only Horus can confirm (H2, H4, H5).

Horus endpoints

  • POST /book-entries.list main
  • POST /account-histories.list main
  • POST /daybooks.list (pick sales or purchase journals, cached)
  • POST /invoices.sales.outstanding.list (sales: payment status, invoice-currency amounts)
  • POST /account-histories.list (second call: payments, when requested)
  • POST /fiscal-years.list (default period without dates, cached)
  • GET /folders.info (legislation for VAT codes, cached)

  • POST /accounts.list (partner account number, cached)
  • GET /book-entries.info (complete changed entries, incremental reads)

What the documentation confirms

Pushed invoices are 'converted into book entries in the corresponding daybook' (guide: Posting sales & purchase invoices). book-entries.list returns entry headers (number, date, confirmed flag, partner, totals, attached document) for one daybook and a month period, with the partner sideloaded on request. account-histories.list returns all entry lines of a period, across several daybooks, with optional VAT, analytic, partner and matching detail. invoices.sales.outstanding.list returns open sales invoices and credit notes with open amount, payment status, transaction type and invoice-currency totals. ModifiedAfter exists on book-entries.list and account-histories.list.

Specificities to be aware of

  • This is the clearest case of one Chift route needing several Horus endpoints: one header call per journal, one or two ledger calls, and the open sales list for sales types. Derived
  • Updating an invoice through the API creates a new book entry with a new id. Ids stored by consumers stop working; reconcile on journal plus number. Documented
  • Incremental sync (updated_after) still reads a whole month window and reports neither deletions nor replaced ids, so a periodic full re-sync is needed. Derived
  • Pagination, day-level dates, payment_status and approval_status have no Horus parameter and are emulated by the connector. Derived
  • There is no purchase-side open-invoice list, so purchase payments and 'paid' status come only from matching on the ledger. Derived

What Horus cannot provide

  • Line quantity, unit price and unit of measure are not stored: lines return quantity 1 and unit price equal to the line amount.
  • delivery_date, payment_term_id, payment_method_id and withholding_tax have no per-invoice field on read and are returned null.
  • No 'cancelled' status and no approval workflow: approval_status stays 'unknown' unless Chift accepts Horus 'Verified' (C18).
  • The purchase VAT kind is not returned, so some purchase tax_codes come back null; rate and amount are still returned.
  • The original currency of paid sales invoices and of all purchase invoices is not readable under the EUR assumption.
  • Partner is_company, first name and last name are not stored: every partner is returned as a company.

Depends on an assumption

  • Invoice or credit note is decided by the journal type; the amount sign decides only in folders without a credit-note journal (Proposal, D1).
  • Ledger amounts are in EUR: foreign-currency invoices come back in EUR unless the open sales list gives the invoice currency (Proposal, D4).
  • Lists return the full result for the period: no paging parameter is documented, so Chift paging is emulated on a cached result.
  • Month periods filter on the entry date; the connector filters to the day and may widen the window by one month.
  • tax_code is rebuilt from the line VAT fields against the folder's accepted combinations; null when ambiguous (Proposal, D2).
  • reference and customer_memo are split from the header comment, whose location on read is undocumented (Proposal, D3; H9).
  • 'paid' is inferred from full matching of the partner line, which also covers offsets by credit notes.

Needs confirmation

  • Horus: can the invoice/credit-note type be exposed on read, and can credit notes sit in invoice journals (H2)?
  • Horus: currency of ledger amounts and direction of CurrencyRate for foreign-currency invoices (H4).
  • Horus: limits on result size, period span, request rate and timeouts for multi-year ledger reads (H5).
  • Horus: does ModifiedAfter catch payments and accountant edits, and do accountant edits also create a new id (H10)?

Client creation

POST /consumers/{consumer_id}/accounting/clients

On Horus, Create client becomes POST /companies.new in the Horus folder. A Chift client is a Horus "company": the one third-party record of a folder, flagged as customer and/or supplier. Most identity, contact and address fields copy across directly or with light formatting. The connector fills the Horus-required fields that Chift does not send (search key, role flags, VAT liability, language, country) by rule. Horus returns only the new id, so the Chift response is built by reading the record back.

Horus calls behind one Chift call

  1. Reference data, cached per folder: GET /folders.info (default language and country), POST /accounts.list (checks account_number exists and is active), POST /countries.list (checks the country code).
  2. Pre-checks with POST /companies.list (proposal): search by VAT number and by external reference, so a duplicate gets a clear Chift error or a hint to use force_merge. Then search by the generated search key to make sure the code is free in the folder.
  3. Create with POST /companies.new: FolderId, generated SearchKey, role flags, one address, contact data and the IBANs in the same call. Horus returns only the new Id.
  4. When force_merge is set, these calls replace step 3. GET /companies.info confirms the id is a supplier in the same folder. POST /companies.update sets IsCustomer = true. POST /ibans.new adds any IBAN not yet stored.
  5. Read back in two to three calls. GET /companies.info gives the stored values, the last-modified date and the search key. POST /ibans.list gives the IBANs and BICs. The receivable account number comes from the cached chart, or from GET /accounts.info. One POST /companies.list call with Include might replace these calls, but that is unconfirmed (H15).
  6. Build the Chift response from what was read back, using the same partner rules as the invoice routes (proposal): one 'main' address, is_company = true, and null for fields Horus does not store.

Key points

  • A Chift client is a Horus 'company': the single third-party record of a Horus folder, flagged as customer and/or supplier. One record holds both roles, which is why force_merge maps cleanly: the existing supplier is flagged as customer instead of being duplicated. Documented

Invoice creation (sale/purchase entry, multiple analytic plans)

POST /consumers/{consumer_id}/accounting/invoices/multi-analytic-plans

On Horus, a Chift sale or purchase entry becomes a book entry created by invoices.sales.new (customer invoices and refunds) or invoices.purchases.new (supplier invoices and refunds), with the PDF in the same call. Most header and line amounts map directly. The work is in four areas: resolving references (folder, daybook, company, accounts, analytic dimensions), turning each Chift tax code into a Horus VAT combination, converting analytic percentages into amounts, and deciding what to do with Chift fields that Horus cannot store.

Horus calls behind one Chift call

  1. Reference data, cached per folder: daybooks.list to pick or check the sales/purchase daybook, accounts.list to check line accounts, cost-schemas.list and cost-sections.list to turn analytic ids into the search keys Horus posts with, and folders.info for the folder legislation (BE/LU), which selects the VAT list. fiscal-years.list is read fresh before each create, because the accountant can close a period at any time.
  2. Partner: companies.info checks that partner_id belongs to the folder and has the customer or supplier role. Without partner_id, companies.list finds the company from partner_info and companies.new creates it if it is missing (proposal). Horus needs a CompanyId before it accepts an invoice.
  3. Duplicate check: book-entries.list filtered on the document number. Horus has no idempotency key and the API has no invoice delete, so this check runs before the create and before any retry (proposal, best effort).
  4. Create: invoices.sales.new for customer_* or invoices.purchases.new for supplier_*, with the PDF in the same multipart call. Horus returns only the new entry Id.
  5. Read-back, skipped when ignore_accounting_id=true: book-entries.info by Id gives the stored number, confirmation status and last-update date. account-histories.list is added only when line-level data is needed, such as the EUR amount of a foreign-currency invoice or the partner's collective account.

Key points

  • One Chift call becomes several Horus calls. Before posting, Horus needs the folder, the daybook, the company and the search keys of accounts and analytic dimensions. Its create call returns only an id, so the Chift response is rebuilt from the request plus a read-back. Documented
  • VAT is the main gap. Chift sends one tax_code per line, but Horus accepts no VAT code: it takes a combination of rate, origin and type (plus three purchase fields), valid only as listed in Horus's BE/LU spreadsheets. Proposal: a connector-owned VAT-code list per folder. Horus must confirm the files are current (H1), and Chift must accept the approach (C2). Assumption
  • Posting status and numbering need Chift decisions. Entries pushed through the API are unconfirmed by default so the accountant can review them, while Chift defaults to 'posted'. Horus invoice numbers are numeric, and invoices have no automatic-numbering option. Proposal: review mode by default, and Number 0 (returned as draft) when no number is sent (C1, C7). Assumption
  • Some fields cannot be mapped: withholding tax, the Dutch G/N split, accrual dates, a forced period or a delivery date in another month, payment terms, and line quantity, unit price and unit. reference survives only inside the comment. Rejecting these inputs or silently dropping them is a Chift product decision (C3), because the create response has no warnings field. Derived
  • Analytics change shape. Per-plan percentages must become amounts on combinations of up to 8 dimensions. Multi-plan splits assume the plans are independent (C9), and small lines may read back with slightly different percentages. Derived
  • There is no undo. The API has no invoice delete, and an update creates a new entry with a new id, so a duplicate or wrong invoice cannot be removed through the integration. Hence the number check before any retry (best effort) and the need for a test folder during development (H17). Derived
VAT: from a Chift tax code to a Horus combination Why tax_code is the most important transformation in this route.

Horus has no VAT-code list and accepts no VAT code on write. Each invoice line carries a combination: rate, origin and type for sales, plus kind and condition for purchases. Only the combinations published by Horus are accepted. They come in two spreadsheets linked from the invoice endpoints, one list per legislation (Belgium, Luxembourg) and direction Documented:

Example: a Belgian domestic sale at 21 % is rate 21, origin 0 ("Vente nationale"), type 0 (National). Documented

Outstanding items (clients and suppliers)

GET /consumers/{consumer_id}/accounting/outstandings

The route returns the open (unpaid or unallocated) items of a folder's customers or suppliers. Horus has open-item lists for both sides, but they are not symmetric. Client items come from the open sales invoices list, which has a native open amount, joined with customer ledger lines. Supplier items are rebuilt by the connector from supplier ledger lines. Each Chift item is therefore assembled from two or three Horus sources, and the connector or Chift handles signs, currency and paging.

Horus calls behind one Chift call

  1. POST /daybooks.list (cached per folder): gives each journal's id, code and type. This feeds journal_id and journal_type, because supplier lines carry only the journal code.
  2. type=client: POST /invoices.sales.outstanding.list for the whole folder (ConfirmedOnly when unposted_allowed=false). Returns open sales invoices, credit notes and linked payments with open amount, due date, invoice-currency amounts and payment remark.
  3. type=client, in parallel: POST /customers.outstanding with no company filter. Returns customer ledger lines, joined on the line id to add account number, matching number and line comment. An open sales row missing from this list triggers GET /account-histories.info (fallback).
  4. type=supplier: POST /suppliers.outstanding with no company filter. Returns supplier ledger lines; the connector computes amount and open amount (Credit − Debit) and filters on Confirmed itself.
  5. Chift side: drop linked payments that Horus lists twice, apply filters, sort, return the requested page and count the total. Optional, off by default (Proposal): GET /book-entries.info per entry for the supplier payment communication and carried-forward details.

Key points

  • Clients and suppliers are built differently. Clients get Horus's documented open amount. Horus has no open-amount list for suppliers, so the connector uses the amount of unmatched ledger lines. Whether partially paid supplier invoices appear at all depends on Horus (H8, a priority-1 question). If they do not, a fallback is needed that reads unmatched ledger lines over a period. Derived
  • One Chift call needs several Horus calls. Clients take two (the open sales list plus customer ledger lines, joined on the line id) and suppliers take one, plus a cached daybook list for journal ids and types. No loop per partner is needed, provided that leaving out the company filter returns the whole folder (to confirm, H8). Derived
  • Horus documents no paging, so Chift fetches the full open-item set and pages it itself. Response time on large folders is unverified (H5), and keeping a short cache between page calls needs Chift's agreement (C14). Derived
  • Not mappable or degraded: payment_method (Horus does not return it on read), original_document (carry-forward flag undefined; null in v1, Proposal), at most one due date per item, and supplier payment_communication (null by default). Horus credit-control data (reminder level, payment status, cash discount) has no Chift field. Item ids are expected to change when the source invoice is updated. Derived
  • Signs and currency are connector proposals that still need agreement. Positive means owed, so credit notes and payments are negative (C5, H2). Open sales invoices keep their own currency and every other line comes back in EUR, so one customer's items can mix currencies (C16, H4). Assumption
  • With unposted_allowed=false, only entries confirmed by the accountant are returned. Entries pushed through the API are unconfirmed by default, so they stay out of that view until the accountant confirms them. Whether the connector can push them as confirmed is the posting-mode decision (C1). Derived

5Key limitations and design considerations

The limitations and design considerations that materially affect the proposed solution, most important first. "Proposed handling" is a recommendation for discussion, not an agreed rule.

1VAT codes exist only as published tax combinations Documented

What Horus does
Horus accepts no VAT code on write and has no VAT-code list. A line is valid only if its rate, origin and type (plus kind and condition on purchases) match a combination listed in two spreadsheets, each with a BE and an LU sheet (F). The TaxOrigin enums in the API reference miss the Luxembourg codes used in the files, and TaxKind is not returned on read (F).
Business implication
GET vat-codes and every tax_code become connector-owned data. Luxembourg folders and folders that are not VAT liable remain uncertain. Some purchase VAT codes come back empty on read. If the files are incomplete, codes that clients need cannot be posted.
Proposed handling
Proposal: build the catalogue from the files, with one list per folder legislation (BE/LU) and direction and one synthetic id grammar (D2). Reject a code outside the folder's list with 422 before calling Horus. Return tax_code = null on read when the match is ambiguous. Book VAT as sent (OverrideTaxAmounts = true, D16). Descoping trigger: a reduced VAT-code list if needed codes cannot be expressed.
To be decided by
Both: Horus confirms that the files are current and which origin list is authoritative (H1); Chift accepts the synthetic catalogue and the VAT-amount policy (C2).
Routes
Invoice creation, invoice retrieval, VAT codes (dependency)

2'Posted' and numbering do not map one to one Documented

What Horus does
Entries pushed through the API are unconfirmed by default, for accountant review. Number is numeric, required, and may be 0 only while the entry is unconfirmed, and invoices have no automatic numbering (F). Whether every licence and user type may set Confirmed = true is not documented (?).
Business implication
A request with Chift's default status 'posted' may come back as 'draft'. An invoice to be confirmed without an invoice_number cannot be posted as confirmed. Numbers such as INV-2024/001 are rejected. An entry pushed without a number cannot be found again after an accountant edit.
Proposed handling
Proposal: a posting mode chosen per connection, either review (default; Confirmed = false) or direct ('posted' sent as Confirmed = true). The response always reports the status actually stored. An invoice without a number is pushed for review and returned as a draft. Non-numeric numbers are rejected with 422, and the number shown to customers goes in reference.
To be decided by
Chift decides (C1, C7); Horus confirms confirmation rights and numbering behaviour (H21, H3).
Routes
Invoice creation, miscellaneous operation creation, invoice retrieval, outstanding items

3No documented paging, limits or timeouts Derived

What Horus does
No Horus list request has paging parameters, ledger reads are bounded by month, and no rate, size or time limit is documented (F: the documentation is silent). That lists return complete result sets is a deduction (D).
Business implication
Unless results are cached between calls, every Chift page may re-read the full period. Behaviour on large accounting-firm folders, including any silent truncation, is unverified. Incremental reads filter headers, but ledger lines are still read per period, so polls stay costly.
Proposed handling
Proposal: a per-folder reference cache plus a short-lived result cache (subject to C14); a bounded default window for invoice retrieval (current fiscal year, C11); a volume test on the largest test folder as the exit criterion of phase 1. Descoping trigger: a mandatory date window or journal filter on invoice retrieval.
To be decided by
Both: Horus states its limits (H5); Chift decides on caching, timeouts and default windows (C14, C11).
Routes
All list routes; most exposed: invoice retrieval, outstanding items

4Invoices are rebuilt from the ledger, without the document type Documented

What Horus does
There is no general invoice list. Headers come from book-entries.list per daybook and period, lines from account-histories.list, and neither exposes invoice vs credit note (F). TransactionType exists only on open sales items (F).
Business implication
This is the most complex read route, with several Horus calls per request. A credit note keyed into the sales daybook of a folder that also has a credit-note daybook comes back as an invoice with negative amounts. Line quantity and unit price are not stored, so on read a line has quantity 1 (proposal).
Proposed handling
Proposal: the daybook type decides; the sign of the partner line is used only in folders without a credit-note daybook; TransactionType is a consistency check, not an override (D1). The rule stays labelled as an assumption until Horus exposes the type.
To be decided by
Both: Horus on credit-note rules and the type on read (H2); Chift chooses which misclassification is acceptable (C5).
Routes
Invoice retrieval; also outstanding items and journals

5Supplier open amounts are computed, not read Derived

What Horus does
Client open items come with a native OpenAmount from invoices.sales.outstanding.list (F). Suppliers have only ledger lines (suppliers.outstanding). Two points are undocumented (?): whether partially matched lines are returned, and whether every partner is returned when CompanyIds is omitted.
Business implication
Payables are complete only if Horus returns partially matched lines, or if a fallback read is used. Otherwise every supplier balance can silently drop partially paid invoices, and this is a Task B route.
Proposed handling
Proposal: open amount = Credit − Debit of each unmatched line. Partially matched groups are netted if Horus returns them (remainder allocated oldest due date first, C5). Fallback: read the supplier concentration accounts with account-histories.list. Control check against Horus's SumDebit/SumCredit. First test case: one partially paid purchase invoice and one partially paid sales invoice.
To be decided by
Horus on completeness and partial matching (H8); Chift on sign, allocation and item granularity (C5, C17).
Routes
Outstanding items (Task B)

6No idempotency key, and ids change on update Documented

What Horus does
A create returns only an Id, and no idempotency key is documented. Invoice and operation updates create a new book-entry Id. Invoices, companies and accounts have no delete endpoint (F).
Business implication
A timeout on create can lead to a duplicate that cannot be deleted. Every create response needs a read-back. Ids kept by client applications stop working after an edit, and an entry pushed without a number has no business key to find it again.
Proposed handling
Proposal: search before every create (VAT number, external reference, account number, document number) and never retry blindly. When the record has no key, return an 'outcome unknown' error. Consumers reconcile on journal and number, and should always send a number.
To be decided by
Chift on the duplicate policy and errors (C6, C7); Horus on duplicate numbers and commits after a timeout (H3).
Routes
All write routes; invoice retrieval

7Currency support differs by object Documented

What Horus does
Invoices accept CurrencyCode and CurrencyRate when the folder allows currencies, but miscellaneous-operation lines have no currency field (F). The currency of ledger amounts on read is not documented, and invoice-currency amounts appear only on open sales items (F).
Business implication
Foreign-currency operations are stored in euro and lose their original currency. On read, a foreign-currency sales invoice may switch from its own currency to euro once paid, and purchase invoices always come back in euro.
Proposed handling
Proposal: never pair euro amounts with a foreign currency code (D4). Convert foreign-currency operations at the supplied rate, as Chift's contract describes, with the rate required; who converts is C15. Verify with one foreign-currency invoice in the test folder. Chift may prefer one stable euro view (C16).
To be decided by
Both: Horus on the currency of ledger amounts (H4); Chift on conversion and representation (C15, C16).
Routes
Miscellaneous operation creation, invoice retrieval, outstanding items, invoice creation (response)

8Third-party master data is narrower than Chift's client Documented

What Horus does
companies.new requires SearchKey, IsVatLiable, LanguageCode and CountryCode; beyond 'unique within the folder', the search-key rules are undocumented. A company holds one address and no person, mobile or notes fields, and a second company with the same VAT number is created only when AllowDuplicateVatNumber is true (default false) (F).
Business implication
The connector invents the customer code that accountants see. Extra addresses and person fields are lost. Duplicate handling must be defined for VAT matches and for clients without a VAT number or external reference.
Proposed handling
Proposal: generate the search key from the name (uppercase, accents removed, truncated, numeric suffix on collision, D10). Keep the main address, else the invoice address. Run a duplicate pre-check that returns 'already exists' with the existing id, and use force_merge for existing suppliers. Apply the same rules to partner_info.
To be decided by
Chift (C8, C3, C6); Horus on search-key rules and field meanings (H7, H11).
Routes
Client creation (Task B), invoice creation (partner_info), supplier creation (dependency)

9Testing runs on real data Documented

What Horus does
Requests run against the license's real database; write tests need a test license or test folder, and no sandbox is documented (F). The registration and Quickstart pages were not in the reviewed documentation (?).
Business implication
None of the assumptions can be checked before Horus provides a test license: VAT acceptance, credit notes, partial matching, currency and volumes. Test invoices and companies cannot be deleted through the API.
Proposed handling
Proposal: Gate 0 before build: register the integration, obtain a test license and folder, and run a volume test. Descoping trigger: no build without a test license.
To be decided by
Horus provides access (H17, H19); Chift makes the go decision.
Routes
All routes (verification); all write routes

Method

Both contracts were read in full for the routes in scope. For each route the same questions were asked: what is the business object, what does Chift require and return, can Horus read or write it, which calls in which order, how each field maps, and what is lost or uncertain. Each mapping was then checked independently against the documentation, and the result was challenged in a critical review. That review led to the corrections in appendix B. No request was sent to a Horus licence or a Chift environment.
