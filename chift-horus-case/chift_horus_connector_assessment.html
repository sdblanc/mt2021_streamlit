Chift product/tech case · Part 1 · Mapping Chift – Horus

Horus connector assessment

Can Chift's accounting routes be served from the Horus Software API, which Horus endpoints would each route use, how the requested attributes map, and what must be confirmed before building.

Prepared by Silas Deblanc For Chift, Product & Tech Date 13 October 2026 Status For discussion Basis desk analysis of the documentation, no live API calls Detailed reference full technical mapping (unchanged; corrections in appendix B)

1Executive summary and feasibility

The Horus Software API has a documented endpoint for the core object of every Chift route in scope, so the documentation rules out none of the 11 routes. That is not the same as every route being settled. One route is confirmed by the documentation (analytic accounts). Six are feasible but rely on assumptions the documentation does not confirm (client creation, journals, ledger account creation, chart of accounts, folders and analytic plans). Four need answers from Horus or decisions from Chift before their design is final (invoice retrieval, invoice creation, miscellaneous operations and outstanding items); these are likely the highest-value routes for Chift’s clients (to confirm with Chift) and carry most of the build effort. Behaviour on large folders cannot be concluded from the documentation for any list route.

What is confirmed, assumed or still open

What the documentation confirms

  • Each of the 11 routes has documented Horus endpoints for its core object and operation (create or list; invoices are listed as book entries and ledger lines) in the documentation reviewed; no route lacks a capability. Documented
  • Invoice creation is native: invoices.sales.new and invoices.purchases.new post invoices and credit notes (Type 0/1) with VAT, analytics and the PDF in one call. Documented
  • Client open items are native: invoices.sales.outstanding.list returns open sales invoices and credit notes with open amount and payment status. Documented
  • Horus publishes the accepted VAT combinations in two spreadsheets (sales, purchases), each with BE and LU sheets, and folders.list returns each folder's legislation. Documented
  • The write rules are documented, so the connector can check them before posting: totals equal base plus tax, cost lines sum to the line base, miscellaneous operations balance. Documented

What depends on an assumption

  • Horus lists return complete results for a folder and period, so paging, totals and day-level filters can be emulated. Deduced from the absence of paging parameters. Derived
  • The VAT spreadsheets are current and complete, and the API accepts the Luxembourg tax origins that are missing from the API reference's value lists. Assumption
  • Invoice or credit note on read follows the daybook type; the amount sign decides only where no credit-note daybook exists. A proposed rule, not documented behaviour. Assumption
  • suppliers.outstanding without a company filter returns every supplier's open lines, partially matched ones included; otherwise a fallback read of supplier ledger lines is needed. Assumption
  • Ledger amounts on read are in the folder currency (EUR). Open sales items, which carry a total and a separate invoice-currency total, suggest it; no source states it. Assumption

What needs confirmation from Horus or Chift

  • Horus, VAT and posting: whether the tax files are current and authoritative (H1), credit-note daybook rules and the document type on read (H2), numbering and duplicate numbers (H3). To confirm
  • Horus, reads: the currency of ledger amounts (H4), rate, size and time limits (H5), and whether the outstanding endpoints return partially matched lines for all partners (H8). To confirm
  • Horus, access: integration registration and a test licence or folder (H19, H17), the allowed API addresses and connection lifecycle (H24), whether every user may confirm entries (H21), and which documentation version is authoritative (H20). To confirm
  • Chift, before build: posting mode and the rule for invoices without a number (C1, C7), caching and timeouts (C14), and who converts foreign-currency operations (C15). To confirm
  • Chift, Task B conventions: the synthetic VAT-code list (C2), sign conventions (C5) and partner codes (C8). To confirm

What cannot be concluded yet

  • Whether the list routes perform and stay complete on large accounting-firm folders: no limits are documented and no volume test has been run. To confirm
  • Whether supplier open items are complete for partly paid invoices. This depends on H8, or on a fallback validated with test data. To confirm
  • Whether every VAT case can be expressed: the files have no variant for non-VAT-liable folders, Luxembourg uses origins missing from the API reference's value lists, and the partial-deduction percentage on purchases (condition PCT, e.g. 35 % on car costs) appears both as 35 and as 0.35 in the sources. To confirm
  • Whether incremental sync catches every change: ModifiedAfter is documented on three lists only, its coverage of matching and accountant edits is undocumented, and no deletion signal is documented (H10). To confirm
  • Whether the mapping holds for the apiary documentation the case links and for the live Chift reference: neither was compared, and no live request was sent. To confirm

Key messages

  • One Chift call often means several Horus calls. Horus needs its own references (journal, partner, account and analytic codes), and a create returns only an id. The connector therefore looks up reference data, cached per folder, and reads records back. Horus has no endpoint that lists all invoices (only open sales invoices and credit notes are listed, without lines), so invoice retrieval is rebuilt from ledger data.
  • VAT is the main mapping gap. Horus accepts no VAT code, only a combination of rate, origin and type (plus kind and condition for purchases), from lists Horus publishes per country and direction. Chift’s tax_code needs a translation table: a proposal Chift must accept and Horus must confirm.
  • Some Chift data has no place in Horus. Examples: line quantity and unit price, several addresses, person names, withholding tax, invoice-level payment terms (Horus keeps terms only on the company), and the account type. Chift must decide whether such inputs are rejected or dropped, and its clients need to know.
  • Accountant review is built into Horus. Entries pushed through the API are unconfirmed by default, and invoices cannot be deleted through the API. Whether Chift’s "posted" should bypass that review is a Chift decision. Proposal: review by default.
  • Two read-side points rest on undocumented behaviour: telling invoices from credit notes when reading entries, and computing supplier open amounts when invoices are partly paid. Both need confirmation from Horus.
RecommendationProceed to a short validation phase rather than a full build. First get a test licence and answers to the "before build" questions in section 6. Then build the reference routes and the simple creates, followed by invoice creation and miscellaneous operations. Leave the ledger-based reads (invoice retrieval, outstanding items) until Horus has confirmed credit notes, currency, partial matching and volumes. This is a proposal for Chift’s decision, not a commitment on behalf of Chift or Horus.

2How Horus differs from Chift

Chift exposes one standard accounting model; Horus has its own vocabulary and rules. The connector sits in between: it translates each Chift request into one or more Horus calls, converts fields, looks up Horus references, and assembles the response. Most of the effort and most of the risk come from the differences below, not from missing objects.

Client creationFeasible with assumptionsCreation, read-back and merge are documented; the search-key format, a few field meanings and the duplicate policy rest on assumptions or Chift decisions, none blocking.

Horus endpoints

  • POST /companies.new main
  • GET /companies.info (read back created client)
  • POST /ibans.list (read back bank accounts)
  • POST /accounts.list (receivable account check, cached)
  • POST /companies.list (duplicate and free-code checks)
  • POST /companies.update (force_merge: supplier becomes customer)
  • POST /ibans.new (force_merge: add IBANs)
  • GET /folders.info (default language and country, cached)
  • POST /countries.list (country code check, cached)

What the documentation confirms

companies.new needs folder, search key, name, role and VAT-liable flags, language and country; it takes VAT number, one address, contacts, IBANs and receivable account, and returns only the id. A duplicate VAT number is refused by default; companies.update is partial.

Specificities to be aware of

  • A Horus 'company' is a customer or supplier inside a folder, not the Chift company or folder. One record can hold both roles, hence force_merge. Documented
  • Horus requires a search key (the third-party code accountants see) that Chift does not send; the connector must generate one per folder. Proposal: derive it from the name (C8). Assumption
  • A VAT number already used by another company is refused by default (AllowDuplicateVatNumber=false), so a client that already exists as a supplier should go through force_merge rather than a duplicate company. Derived
  • No idempotency key and no company delete endpoint: a blind retry can leave an undeletable duplicate, so the connector searches before retrying. Derived

What Horus cannot provide

  • One address per company: extra invoice or delivery addresses are lost.
  • mobile, internal_notes, first_name, last_name, function, company_id: no field; dropped and returned null. Currency is read-only.
  • is_company=false: no company/individual flag, so every client comes back as a company.
  • Enterprise number of a VAT-liable client, and non-IBAN bank accounts, cannot be stored.

Depends on an assumption

  • Proposal (C8): search key generated from the name, numeric suffix on collision (Horus rules undocumented); missing language and country taken from folder defaults.
  • Undocumented field use: active=false as CustomerActivitySuspended; a non-VAT-liable client's company_number as VatNumber; phone and website read back from ContactPhone and ContactWebsite.
  • Proposal: duplicates are caught by a pre-check on VAT number and external reference, since Horus documents no idempotency key.

Needs confirmation

  • Horus: search-key rules and duplicate-key error (H7, H6); meaning of CustomerActivitySuspended, how an enterprise number is written, default receivable account (H11).
  • Horus: is the duplicate-VAT check per folder, and does it ignore spaces and dots (H25)?
  • Chift: search-key convention, duplicate behaviour, force_merge policy, and whether unstorable fields or extra addresses are rejected or dropped (C8, C6, C3).

Not yet concluded

  • Whether a timed-out create can still be committed later; until known, the check before a retry is best effort (H3).
  • Whether companies.list can include IBANs and the receivable account in one call, shortening the read-back (H15).

Horus endpoints

  • POST /invoices.sales.outstanding.list (sales: payment status, invoice currency)

What the documentation confirms

Pushed invoices become book entries in their daybook. book-entries.list gives headers per daybook and month period, account-histories.list gives lines with VAT, analytics and matching (both accept ModifiedAfter); the open sales list adds open amount, payment status, invoice currency.

Specificities to be aware of

  • Query parameters shape the calls: date_from/date_to become the month window Horus requires (StartMonth/EndMonth) and are re-filtered to the day; journal_ids choose the daybooks read, one header call each; include_payments adds one ledger call; include_partner_info adds none, because book-entries.list can return the partners in the same response (Include = CompanyDetail.Company). The ledger-line call is made even when include_invoice_lines=false: payment status, due dates and currency come from the partner line. Derived
  • Updating an invoice creates a new book entry with a new id, so stored ids stop working; reconcile on journal plus number. Documented
  • Paging, day-level dates, payment_status and approval_status have no Horus parameter and are emulated; updated_after still reads a month window and misses deletions, so periodic full re-sync is needed. Derived
  • There is no purchase-side open-invoice list, so purchase payment status comes only from matching on the ledger. Derived

What Horus cannot provide

  • Line quantity, unit price and unit: not stored; lines return quantity 1 and unit price equal to the line amount.
  • delivery_date, payment_term_id, payment_method_id, withholding_tax and partner first and last names: no field on read; returned null.
  • No 'cancelled' status or approval workflow: approval_status stays 'unknown' unless Chift accepts Horus 'Verified' (C18).
  • Purchase VAT kind is not returned, so some tax_codes are null. Ledger lines carry a currency code and rate, but whether their amounts are in EUR or in that currency is undocumented (H4).

Depends on an assumption

  • Proposal (H2, C2): invoice or credit note is decided by journal type; tax_code is rebuilt from line VAT fields, null when ambiguous.
  • Proposal (H4, C16): ledger amounts are EUR, so foreign-currency invoices return in EUR unless the open sales list gives the invoice currency.
  • Lists return full results (no paging documented); 'paid' is inferred from full matching; reference and memo are split from the header comment (H9).

Needs confirmation

  • Horus: can the document type be read, and can credit notes sit in invoice journals (H2)? Currency of ledger amounts and CurrencyRate direction (H4)?
  • Horus: limits on result size, period and request rate (H5); does ModifiedAfter catch payments and accountant edits (H10)?
  • Chift: default period, draft handling and re-sync cadence (C10, C11); acceptable misclassification (C5); invoice currency or stable EUR view (C16).

Not yet concluded

  • Performance on large folders: Horus documents no limits and no request was sent; to be measured on a test folder.
  • How deleted or replaced invoices are detected: no deletion signal is documented; webhooks are mentioned but not documented.
  • Whether the open sales invoices list ever returns fully paid invoices.

What the documentation confirms

Both endpoints take header totals, lines with VAT fields and analytics, currency, comment and an optional file. Horus checks that totals add up and accepts only its published tax combinations. Entries are unconfirmed by default; create returns only the id.

Specificities to be aware of

  • VAT is the main risk: Horus accepts no VAT code; each line needs rate, origin and type (plus kind and condition for purchases) from an accepted combination. Documented
  • Numbers must be numeric and the API does not number invoices automatically; a number such as INV-2024/001 belongs in reference, not invoice_number. Derived
  • API entries are unconfirmed by default, while Chift defaults to 'posted'; the response must report the status actually stored. Documented
  • No endpoint deletes an invoice, so a wrong or duplicate one needs the accountant; hence a best-effort duplicate-number check before creating and before any retry. Derived

What Horus cannot provide

  • withholding_tax and nl_payment_terms_split: no Horus field (Belgian and Luxembourg folders only). Proposal: reject with 422 (C3).
  • start_date, end_date, delivery_date, force_financial_period, payment_term_id: no field; the period follows the invoice date (Proposal: reject or log, C3).
  • Line quantity, unit price and unit are not stored; reference shares the header comment with customer_memo and cannot be filtered.
  • Automatic numbering unavailable (Proposal: unnumbered invoices go to review as draft, C7); currencies outside Horus's list are rejected.

Depends on an assumption

  • Proposal (C2): each Chift tax_code is a connector-owned id for one accepted Horus VAT combination; VAT amounts are booked as sent.
  • Proposal (C1, H2): posting mode per connection, review (unconfirmed, default) or direct; credit notes sent as Type 1 with positive amounts.
  • Proposal (C9, C8): analytic percentages per plan become amounts on combined cost lines; partner_info.account_number is read as the third-party code.

Needs confirmation

  • Horus: are the tax-combination files current and complete, how are invalid combinations rejected (H1)? A test folder, since invoices cannot be deleted (H17).
  • Horus: numbering, number uniqueness and timed-out creates (H3); credit notes in invoice journals, negative amounts (H2); currency (H4); may every user confirm (H21)?
  • Chift: posting mode and meaning of 'draft' (C1); rule for unnumbered invoices (C7); reject or drop unstorable inputs (C3); meaning of partner_info.account_number (C8).

Not yet concluded

Client creation

POST /consumers/{consumer_id}/accounting/clients

On Horus, Create client becomes POST /companies.new in the Horus folder. A Chift client is a Horus "company": the one third-party record of a folder, flagged as customer and/or supplier. Most identity, contact and address fields copy across directly or with light formatting. The connector fills the Horus-required fields that Chift does not send (search key, role flags, VAT liability, language, country) by rule. Horus returns only the new id, so the Chift response is built by reading the record back.

Horus calls behind one Chift call

  1. Reference data, cached per folder: GET /folders.info (default language and country), POST /accounts.list (checks account_number exists and is active), POST /countries.list (checks the country code).
  2. Pre-checks with POST /companies.list (proposal): search by VAT number and by external reference, so a duplicate gets a clear Chift error or a hint to use force_merge. Then search by the generated search key to make sure the code is free in the folder.
  3. Create with POST /companies.new: FolderId, generated SearchKey, role flags, one address, contact data and the IBANs in the same call. Horus returns only the new Id.
  4. When force_merge is set, these calls replace step 3. GET /companies.info confirms the id is a supplier in the same folder. POST /companies.update sets IsCustomer = true. POST /ibans.new adds any IBAN not yet stored.
  5. Read back in two to three calls. GET /companies.info gives the stored values, the last-modified date and the search key. POST /ibans.list gives the IBANs and BICs. The receivable account number comes from the cached chart, or from GET /accounts.info.
  6. Build the Chift response from what was read back, using the same partner rules as the invoice routes (proposal): one 'main' address, is_company = true, and null for fields Horus does not store.

Key points

  • One record holds both roles, which is why force_merge maps cleanly: the existing supplier is flagged as customer instead of being duplicated. Documented
  • One Chift call needs several Horus calls. Horus create calls return only an id, so the company, its IBANs and (unless cached) its receivable account are read back to build the Chift response. That is two to three extra calls, and about three to seven in total with the checks. Rate limits are undocumented (H5). Derived
  • Horus requires a search key, role flags, a VAT-liability flag, a language and a country that Chift may not send. The search key is the main business choice, because it becomes the client's code that accountants see. Proposal: generate it from the name. The convention is to agree with Chift (C8) once Horus states the rules (H7). Assumption
  • Some data cannot be stored: extra addresses, mobile, notes, person fields, job title, company link, client currency, non-IBAN bank accounts, and the enterprise number of VAT-liable clients. Individuals come back as companies. Client applications must keep this data on their side. Whether to reject or drop such input is a Chift decision (C3). Derived
  • Duplicates: by default Horus refuses a VAT number that is already used, and it documents no idempotency key. Proposal: search by VAT number and external reference before creating, and never retry blindly after a timeout. Without either value there is no reliable duplicate check (C8). Derived
  • Still open for this route: the merge policy (C6), the error codes (C20), the meaning of the 'suspended' flag used for active (H11), and a test folder (H17). Writes go to real data, and the API has no call to delete a company. Derived

Invoice creation (sale/purchase entry, multiple analytic plans)

POST /consumers/{consumer_id}/accounting/invoices/multi-analytic-plans

On Horus, a Chift sale or purchase entry becomes a book entry created by invoices.sales.new (customer invoices and refunds) or invoices.purchases.new (supplier invoices and refunds), with the PDF in the same call. Most header and line amounts map directly. The work is in four areas: resolving references (folder, daybook, company, accounts, analytic dimensions), turning each Chift tax code into a Horus VAT combination, converting analytic percentages into amounts, and deciding what to do with Chift fields that Horus cannot store.

Horus calls behind one Chift call

  1. Reference data, cached per folder: daybooks.list to pick or check the sales/purchase daybook, accounts.list to check line accounts, cost-schemas.list and cost-sections.list to turn analytic ids into the search keys Horus posts with, and folders.info for the folder legislation (BE/LU), which selects the VAT list. fiscal-years.list is read fresh before each create, because the accountant can close a period at any time.
  2. Partner: companies.info checks that partner_id belongs to the folder and has the customer or supplier role. Without partner_id, companies.list finds the company from partner_info and companies.new creates it if it is missing (proposal). Horus needs a CompanyId before it accepts an invoice.
  3. Duplicate check: book-entries.list filtered on the document number. Horus has no idempotency key and the API has no invoice delete, so this check runs before the create and before any retry (proposal, best effort).
  4. Create: invoices.sales.new for customer_* or invoices.purchases.new for supplier_*, with the PDF in the same call. Horus returns only the new entry Id.
  5. Read-back, skipped when ignore_accounting_id=true: book-entries.info by Id gives the stored number, confirmation status and last-update date. account-histories.list is added only when line-level data is needed, such as the EUR amount of a foreign-currency invoice or the partner's collective account.

Key points

  • One Chift call becomes several Horus calls. Before posting, Horus needs the folder, the daybook, the company and the search keys of accounts and analytic dimensions. Its create call returns only an id, so the Chift response is rebuilt from the request plus a read-back. Documented
  • VAT is the main gap. Chift sends one tax_code per line, but Horus accepts no VAT code: it takes a combination of rate, origin and type (plus three purchase fields), valid only as listed in Horus's BE/LU spreadsheets. Proposal: a connector-owned VAT-code list per folder. Horus must confirm the files are current (H1), and Chift must accept the approach (C2). Assumption
  • Posting status and numbering need Chift decisions. Entries pushed through the API are unconfirmed by default so the accountant can review them, while Chift defaults to 'posted'. Horus invoice numbers are numeric, and invoices have no automatic-numbering option. Proposal: review mode by default, and Number 0 (returned as draft) when no number is sent (C1, C7). Assumption
  • Some fields cannot be mapped: withholding tax, the Dutch G/N split, accrual dates, a forced period or a delivery date in another month, payment terms, and line quantity, unit price and unit. reference survives only inside the comment. Rejecting these inputs or silently dropping them is a Chift product decision (C3), because the create response has no warnings field. Derived
  • Analytics change shape. Per-plan percentages must become amounts on combinations of up to 8 dimensions. Multi-plan splits assume the plans are independent (C9), and small lines may read back with slightly different percentages. Derived
  • There is no undo. The API has no invoice delete, and an update creates a new entry with a new id, so a duplicate or wrong invoice cannot be removed through the integration. Hence the number check before any retry (best effort) and the need for a test folder during development (H17). Derived

Horus has no VAT-code list and accepts no VAT code on write. Each invoice line carries a combination: rate, origin and type for sales, plus kind and condition for purchases. Outstanding items (clients and suppliers)

GET /consumers/{consumer_id}/accounting/outstandings

The route returns the open (unpaid or unallocated) items of a folder's customers or suppliers. Horus has open-item lists for both sides, but they are not symmetric. Client items come from the open sales invoices list, which has a native open amount, joined with customer ledger lines. Supplier items are rebuilt by the connector from supplier ledger lines. Each Chift item is therefore assembled from two or three Horus sources, and the connector or Chift handles signs, currency and paging.

Horus calls behind one Chift call

  1. POST /daybooks.list (cached per folder): gives each journal's id, code and type. This feeds journal_id and journal_type, because supplier lines carry only the journal code.
  2. type=client: POST /invoices.sales.outstanding.list for the whole folder (ConfirmedOnly when unposted_allowed=false). Returns open sales invoices, credit notes and linked payments with open amount, due date, invoice-currency amounts and payment remark.
  3. type=client, in parallel: POST /customers.outstanding with no company filter. Returns customer ledger lines, joined on the line id to add account number, matching number and line comment. An open sales row missing from this list triggers GET /account-histories.info (fallback).
  4. type=supplier: POST /suppliers.outstanding with no company filter. Returns supplier ledger lines; the connector computes amount and open amount (Credit − Debit) and filters on Confirmed itself.
  5. Chift side: remove payments that appear twice, apply filters, sort, return the requested page and count the total. Optional, off by default (Proposal): GET /book-entries.info per entry for the supplier payment communication and carried-forward details.

Key points

  • Clients and suppliers are built differently. Clients get Horus's documented open amount. Horus has no open-amount list for suppliers, so the connector uses the amount of unmatched ledger lines. Whether partially paid supplier invoices appear at all depends on Horus (H8, a before-build question). If they do not, a fallback is needed that reads unmatched ledger lines over a period. Derived
  • No loop per partner is needed, provided that leaving out the company filter returns every partner of the folder (to confirm, H8). Derived
  • Horus documents no paging, so the connector fetches the full open-item set and pages it itself. Response time on large folders is unverified (H5), and keeping a short cache between page calls needs Chift's agreement (C14). Derived
  • Not mappable or degraded: payment_method (Horus does not return it on read), original_document (carry-forward flag undefined; null in v1, Proposal), at most one due date per item, and supplier payment_communication (null by default). Horus credit-control data (reminder level, payment status, cash discount) has no Chift field. Item ids are expected to change when the source invoice is updated. Derived
  • Signs and currency are connector proposals that still need agreement. Positive means owed, so credit notes and payments are negative (C5, H2). Open sales invoices keep their own currency and every other line comes back in EUR, so one customer's items can mix currencies (C16, H4). Assumption
  • With unposted_allowed=false, only entries confirmed by the accountant are returned. Entries pushed through the API are unconfirmed by default, so they stay out of that view until the accountant confirms them. Whether the connector can push them as confirmed is the posting-mode decision (C1). Derived

Limitations behind it

The limitations and design considerations that materially affect the proposed solution, most important first.

1VAT codes exist only as published tax combinations Documented

What Horus does
Horus accepts no VAT code and has no VAT-code list. A line's rate, origin and type (plus kind and condition on purchases) must match a published combination. The API reference's value lists omit the Luxembourg origins used in the files, and the VAT kind is not returned on read.
Business implication
GET vat-codes and every tax_code become connector-owned data. Luxembourg and non-VAT-liable folders remain uncertain, some purchase codes come back empty on read, and codes missing from the files cannot be posted.
Proposed handling
Proposal: one VAT-code list per folder legislation (BE/LU) and direction, built from the files. Codes not on the folder's list are rejected before calling Horus; ambiguous codes return null on read. Fallback if Horus cannot confirm the files: start with a reduced VAT-code list.
To be decided by
Horus, on the files (H1); Chift, on the synthetic list and the VAT-amount policy (C2).
Routes
Invoice creation, invoice retrieval, VAT codes (dependency)

2'Posted' and numbering do not map one to one Documented

What Horus does
API entries are unconfirmed by default, for accountant review. Numbers are numeric and may be 0 only while unconfirmed, and invoices have no automatic numbering. Whether every licence and user may confirm entries is undocumented.
Business implication
A 'posted' request may be stored as a draft. An invoice to be confirmed without a number cannot be posted as confirmed (for purchases, whose Number is nullable, the effect of an empty number is undocumented, H3), and numbers such as INV-2024/001 are rejected. Unnumbered entries cannot be found again after an accountant edit.
Proposed handling
Proposal: a posting mode per connection, review (default; entries unconfirmed) or direct ('posted' confirmed), always reporting the status actually stored. An invoice without a number is pushed for review and returned as a draft; the printed number goes in reference.
To be decided by
Chift (C1, C7); Horus, on confirmation rights and numbering (H21, H3).
Routes
Invoice creation, miscellaneous operation creation, invoice retrieval, outstanding items

3No documented paging, limits or timeouts Derived

What Horus does
No Horus list has paging parameters, ledger reads are bounded by month, and no rate, size or time limit is documented. That lists return complete results is a deduction, not a documented fact.
Business implication
Without a cache, each Chift page may re-read the whole period. Behaviour on large accounting-firm folders, including any silent truncation, is unverified, and incremental polls still read ledger lines per period.
Proposed handling
Proposal: cache reference data per folder and results between page calls (C14), default invoice retrieval to the current fiscal year (C11), and run a volume test on the largest test folder. Fallback if volumes are a problem: make a date window mandatory on invoice retrieval.
To be decided by
Horus, on its limits (H5); Chift, on caching, timeouts and default windows (C14, C11).
Routes
All list routes; most exposed: invoice retrieval, outstanding items

4Invoices are rebuilt from the ledger, without the document type Documented

What Horus does
No endpoint lists all invoices: invoices.sales.outstanding.list returns only open sales invoices and credit notes, without lines. Headers come from book-entries.list per daybook and period, lines from account-histories.list, and neither says invoice or credit note. The document type appears only on open sales items and on attached documents (documents.list/.info), so it cannot classify every entry.
Business implication
The most complex read route, with several Horus calls per request. A credit note keyed into a sales daybook, in a folder that also has a credit-note daybook, reads back as an invoice with negative amounts. Quantity and unit price are not stored.
Proposed handling
Proposal: the daybook type decides; the amount sign is used only in folders without a credit-note daybook; the open-items type serves as a consistency check, not an override. The rule stays an assumption until Horus exposes the type.
To be decided by
Horus on credit-note rules and the type on read (H2); Chift on acceptable misclassification (C5).
Routes
Invoice retrieval; also outstanding items and journals

5Supplier open amounts are computed, not read Derived

What Horus does
Client open items come with a native open amount. Suppliers have only ledger lines from suppliers.outstanding. Whether partially matched lines are returned, and whether every supplier is returned without a company filter, is undocumented.
Business implication
If partially matched lines are missing, supplier balances silently drop partly paid invoices. This affects a Task B route.
Proposed handling
Proposal: an unmatched line is open for its full amount; partly matched groups are netted if Horus returns them; otherwise supplier ledger lines are read as a fallback. First test: one partly paid purchase invoice and one partly paid sales invoice.
To be decided by
Horus on completeness and partial matching (H8); Chift on signs and allocation (C5, C17).
Routes
Outstanding items (Task B)

6No idempotency key, and ids change on update Documented

What Horus does
A create returns only an Id, and no idempotency key is documented. Updating an invoice or operation creates a new Id. Invoices, companies and accounts cannot be deleted through the API.
Business implication
A timed-out create can leave a duplicate that cannot be deleted. Every create needs a read-back to build the Chift response. Ids stored by client applications stop working after an edit.
Proposed handling
Proposal: best-effort duplicate check before every create and any retry (VAT number, external reference, account or document number); never retry blindly; return an 'outcome unknown' error when the record has no key. Consumers should always send a number. Once Horus has returned an id, the request never ends in an error: if the read-back fails or shows a mismatch, the response is built from the request (operation_number null when Horus generated it) and the read-back is retried later, because a client retry could book a second entry that the API cannot delete.
To be decided by
Chift on the duplicate policy and errors (C6, C7); Horus on duplicates and commits after a timeout (H3).
Routes
All write routes; invoice retrieval

7Currency support differs by object Documented

What Horus does
Invoices accept a currency code and rate when the folder allows currencies; miscellaneous-operation lines have no currency field. On read, ledger lines carry a currency code and rate, but whether their amounts are in EUR or in that currency is undocumented; separate invoice-currency amounts appear only on open sales items.
Business implication
Foreign-currency operations are stored in euro without their original currency. On read, under the proposed EUR reading of ledger amounts (until H4 is answered), a foreign-currency sales invoice switches to euro once paid, and purchase invoices come back in euro.
Proposed handling
Proposal: convert foreign-currency operations at the exchange rate that Chift's contract requires, rather than reject them; never pair euro amounts with a foreign currency code. Verify with one foreign-currency invoice in the test folder.
To be decided by
Horus on the currency of ledger amounts (H4); Chift on who converts and how currency is shown (C15, C16).
Routes
Miscellaneous operation creation, invoice retrieval, outstanding items, invoice creation (response)

8Third-party master data is narrower than Chift's client Documented

What Horus does
companies.new requires a search key, VAT liability, language and country; search-key rules beyond uniqueness are undocumented. A company holds one address and no person, mobile or notes fields, and a duplicate VAT number is refused by default.
Business implication
The connector invents the customer code that accountants see. Extra addresses and person fields are lost. A duplicate policy is needed, including for clients without a VAT number or external reference.
Proposed handling
Proposal: generate the search key from the name, with a numeric suffix on collision; keep the main address, else the invoice address; pre-check duplicates and return the existing id; use force_merge for existing suppliers.
To be decided by
Chift (C8, C3, C6); Horus on search-key rules and field meanings (H7, H11).
Routes
Client creation (Task B), invoice creation (partner_info)

9Testing runs on real data Documented

What Horus does
Requests run against the licence's real database; write tests need a test licence or test folder, and no sandbox is documented. The registration and Quickstart pages were not available for this analysis.
Business implication
No assumption can be checked until Horus provides a test licence: VAT acceptance, credit notes, partial matching, currency and volumes. Test invoices and companies cannot be deleted through the API.
Proposed handling
Proposal: in the validation phase, register the integration, obtain a test licence and folder, and run a volume test. Go/no-go condition: no build without a test licence.
To be decided by
Horus, on registration and test access (H17, H19); Chift, on the go decision.
Routes
All routes (verification); all write routes

Method

Both contracts were read in full for the routes in scope. For each route the same questions were asked: what is the business object, what does Chift require and return, can Horus read or write it, which calls in which order, how each field maps, and what is lost or uncertain. Each mapping was then checked independently against the documentation, and the result was challenged in a critical review. That review led to the corrections in appendix B. No request was sent to a Horus licence or a Chift environment.

How to read the labels

Documented stated in a source · Derived deduced from the sources (for example from the absence of a field) · Assumption a proposal or interpretation that must be confirmed · To confirm not documented. A label rates the mapping or statement itself: a row whose mapping is a proposal or an interpretation is labelled Assumption, even when it uses documented Horus fields. Smaller proposals inside a row (validation, defaults, how to reject) are marked "Proposal" in the text. In sections 2 and 5 the label describes the Horus behaviour; proposals there are also marked "Proposal".
