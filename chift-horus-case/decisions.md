# Cross-route harmonisation decisions (binding for all route mappings)

These decisions resolve the inconsistencies found by the final critic. Apply every decision that touches your route. Where a decision depends on undocumented Horus behaviour, label the resulting rows "A" and keep or add the open question listed.

## D1. Credit notes and daybooks (create ↔ read round-trip)
- **Write (create_invoice):** keep the daybook auto-selection fallback. customer_invoice → [200]; customer_refund → [250], falling back to [200] if the folder has no 250 daybook; supplier_invoice → [100]; supplier_refund → [150], falling back to [100]. Refunds are posted with Type=1 and positive amounts (D16). Exactly one candidate daybook must remain, otherwise 400 'journal_id required'. The Horus guide does not tie Type to a daybook type, so keep the open question: "Can a credit note (Type 1) be posted into a 200/100 daybook, and an invoice into 250/150?"
- **Read (get_invoices):** ALWAYS scan both sibling daybook types (customer_* → 200 + 250; supplier_* → 100 + 150). Proposed rule (revised after review), daybook first: 250/150 = credit note, 200/100 = invoice. Only in a folder without a 250 (150) daybook, where the write fallback posts refunds into 200 (100), classify entries of that daybook by the partner-line sign (customer: net credit = credit note; supplier: net debit = credit note). TransactionType on open sales items is a consistency check (log mismatches), never an override, so the class is stable when the item is paid. Known failure: an accountant's credit note keyed into 200/100 in a folder that has 250/150 is returned as an invoice with negative amounts; the alternative sign-first rule fails instead on every credit-direction invoice, which Chift's due-date convention allows. Label A until Horus confirms or exposes the Type (H2); Chift chooses (C5). Outstanding items apply the same marker: rows of invoices.sales.outstanding.list take their sign from TransactionType (0 +, 1 −); payments and misc rows keep the raw sign (see D5).
- **Journals (journals_folders):** state that credit notes may sit in 200/100 daybooks, so journal_type describes the daybook, not every entry in it.

## D2. One canonical synthetic VAT-code grammar
Horus has no VAT-code list endpoint and accepts no VAT code on write (on read, VatDetail.VatCode/VatHeading exist, but they are undocumented output-only strings, not an "internal code"). The connector owns a VAT catalogue built from the Horus tax-combination files (the two spreadsheets linked from the invoices.*.new/update reference pages, downloaded 13 Oct 2026, appendix_horus_tax_combinations.md), with one list per folder Legislation (BE/LU, read from folders.info) and direction (sales/purchases). One id grammar, used identically by GET vat-codes (folder-scoped), create_invoice (decode) and get_invoices (encode):
- Sales: `S-{TaxRate}-{TaxOrigin}-{TaxType}`, plus `-{TaxCountryCode}` for OSS rows (BE TaxOrigin 13; LU 24, 26, 29; rate and country supplied per transaction). Example: `S-21-0-0`.
- Purchases: `P-{TaxRate}-{TaxOrigin}-{TaxType}-{TaxKind}-{TaxCondition}-{TaxConditionValue}`, with `x` for a component that is not used. Example: `P-21-2-0-0-1-true`. On LU COUNTRY rows (TaxCondition 0), the condition value is the country code.
- **Validation:** against the folder's list for the invoice direction, never against the reference TaxOrigin enums (they lack the LU codes, and several labels differ from the files). Labels for GET vat-codes come from the files.
- **Canonical rendering:** rates as whole numbers as in the files (all file rates are whole); TaxConditionValue as in the invoices.purchases.new enum (true/false/35/50/75/85; the purchases "Available values" sheet shows 0.35… → discrepancy question in H1); `x` for unused; rows with rate/country "XX" (sales OSS: BE 13, LU 24/26/29; LU purchases COUNTRY: 44/49) carry the transaction's rate and country. Published ids never change; catalogue updates only add ids.
- **Read rule:** build the id from VatDetail (VatRate, SaleTaxOrigin/PurchaseTaxOrigin, TaxType, TaxCountryCode, TaxCondition, TaxConditionValue) and return it only if exactly one catalogue entry matches. VatDetail has NO TaxKind, so when several purchase entries match (differing only by TaxKind), or none does, return tax_code = null and keep tax_rate/tax_amount. Never guess, and never return Horus VatCode as the Chift tax_code.
- **VAT amounts booked as sent:** OverrideTaxAmounts=true on every invoice (proposal, D16; Chift question C2). Horus's 1-cent recalculation default is documented.
- Open questions to Horus (H1): confirm the files are current and complete, how changes are announced, how an invalid combination is rejected, and which TaxOrigin list is authoritative (reference enums vs LU files); the combination for non-VAT-liable folders; the meaning of VatCode; can TaxKind be exposed on read? Read-side TaxCondition has an extra value '4 = Article'.

## D3. Invoice header Comment convention (reference + customer_memo)
- **Write:** Horus header Comment = `{reference}` when only reference is set; `{reference} | {customer_memo}` when both are set; `| {customer_memo}` when only customer_memo is set (the leading separator means "no reference"). Separator = space, pipe, space. Label D for the rule. Comment length limits are undocumented (?).
- **Read (get_invoices, outstandings):** take the header comment, split on the first ` | `: left → reference (null if empty), right → customer_memo. Where the header Comment surfaces on read is undocumented. Read it from the partner-line Comment (account history) first, then book-entries RemarkCompany, then (open sales list) Remark, and label it A. Add the open question to Horus: "Where does the invoice header Comment surface on read (partner-line Comment, RemarkCompany, Remark)?"

## D4. Currency of amounts (one assumption everywhere)
- **Assumption (A, everywhere):** account-history Debit/Credit and book-entry CompanyDetail amounts are in the folder currency (EUR). Invoice-currency amounts are known only from (a) the write echo on create, or (b) TotalCurrencyAmount / OpenCurrencyAmount on invoices.sales.outstanding.list.
- **Rule:** never pair EUR amounts with a foreign currency code. For a foreign-currency document where invoice-currency amounts are not available, return the amounts in EUR with currency = 'EUR' and currency_exchange_rate = 1, flag it as a limitation, and keep the open question "Direction and meaning of CurrencyRate; currency of CompanyDetail amounts". accounting_info.main_currency_total = the EUR partner-line amount. Outstanding items: currency_exchange_rate = TotalAmount / TotalCurrencyAmount of the returned row, so the rate always matches the amounts returned; CurrencyRate is not passed through until its direction is known (H4).
- Applies to get_invoices, outstandings (supplier lines and client fallback lines) and create_invoice (response rebuilding).
- **Consumer-visible effect:** an open foreign-currency sales invoice is returned in its currency and switches to EUR once paid; purchases always EUR. Chift chooses (C16) between this (disclosed) and one stable EUR view until H4 (analyst's preference).
- **Miscellaneous operations (LD6):** the posting body has no currency field, so amounts are stored in EUR. Non-EUR operations are converted at the supplied rate (by Chift core, or by the connector as a fallback: line by line, rounded to 2 decimals, 422 if rounding unbalances the entry unless Chift defines a residue rule; C15). They are never rejected and never posted unconverted. The rate is required when currency ≠ EUR (1 counts as missing, since it is the Chift default). The original currency is not kept. The response never pairs EUR amounts with a foreign code.
- **Why EUR, and what could prove it wrong:** invoices.sales.outstanding.list returns TotalAmount next to TotalCurrencyAmount (and OpenAmount next to OpenCurrencyAmount), which suggests base amounts are in EUR. The opposite reading must be ruled out: account-histories.list describes CurrencyCode as "The currency used for this account history", which could mean Debit/Credit are in that currency; then D4 would return foreign amounts labelled EUR. H4 asks; verify with one foreign-currency invoice in the test folder before go-live.

## D5. Sign convention for outstanding items
- Lines read from the customer side (customers.outstanding, customer concentration accounts): amount = Debit − Credit; match-group residual = Σ(Debit − Credit).
- Lines read from the supplier side (suppliers.outstanding, supplier concentration accounts): amount = Credit − Debit; residual = Σ(Credit − Debit).
- Rows of invoices.sales.outstanding.list: sign from TransactionType (0 invoice +, 1 credit note −); payments (2) and misc rows (3) keep the raw sign (a refund paid out to a customer has the opposite sign of a received payment); disagreements are logged. The Horus examples show no credit note, so the native sign is not relied on.
- A line whose AccountType differs from the expected value is kept and logged, never dropped silently: inclusion and sign follow the endpoint or account the line was read from.
- Positive therefore means "owed": receivable for clients, payable for suppliers. Apply the same side-based formula in every client and supplier path (primary, reconciliation lines, fallbacks). Open question to Chift: the expected sign convention for OutstandingItem.amount/open_amount.
- Partly matched groups (only if Horus returns them, H8): residual allocated to the invoice-side lines oldest DueDate first (A; pro-rata is the alternative; partner totals unchanged).
- Chift's due_dates convention is a document view (customer credit note positive): C5 asks which view Chift wants for outstanding items.

## D7. One folder_id rule (every route)
folder_id is required whenever the connection has more than one selected folder. If exactly one folder was selected at activation, use it. If no selection is stored, use the single folder returned by POST /folders.list {Mode: 0}. Otherwise return 400 'folder_id required'. Horus 403 → Chift 400 'access denied for the connected Horus user (folder or action)', with the Horus Details.
A folder_id that is not in the stored activation selection is rejected with 400 "folder not selected for this connection" before any Horus call, on every folder-scoped route (Chift FolderItem.selected: "Requests targeting a folder that was not selected will be rejected"). This is defence in depth: one Horus grant covers every folder the authorising user can access, so isolation otherwise rests on Chift's folder selection and on D13. If Chift confirms that its platform enforces this upstream (C12), state it here once and drop the connector check. Get folders is not affected.

## D8. Analytics: one cache, one rounding rule, one Free-schema policy
- One per-folder cache: POST /cost-schemas.list, plus POST /cost-sections.list per List-type schema with Filter.IncludeInactive = true. Write routes (create_invoice, create_misc_operation) reject an inactive section with 422 and resolve schema/section search keys only from this folder-scoped cache (no per-call cost-sections.info / cost-schemas.info).
- Chift ids: analytic_plan = cost schema GUID Id; analytic_account = cost section GUID Id. Posting converts them to SchemaSearchKey / Value (section SearchKey) through the cache.
- Rounding: percentages → amounts use the largest-remainder method on the per-line product allocation, so the cost lines sum exactly to the line BaseAmount (cross-cutting convention aligned to this). Combination rows that round to 0.00 are dropped; rows per invoice line are capped (proposal: 100). Tie-break: plan order, then account id. Read side: a plan whose cost lines do not sum to the line BaseAmount is omitted with a warning (never rescaled to 100%). Disclose the small-amount round trip (0.10 sent 33/33/34 → read back 30/30/40).
- Free schemas (CostSectionType 900): excluded from Chift analytics in v1. They are not returned by Get analytic plans/accounts, not accepted on write, and omitted on read (flag a warning). Keep the open question. A folder with a Mandatory Free schema rejects analytics on write with 422 in v1 (proposal).

## D9. One shared Horus company → Chift partner mapper
Used identically by the create_client response, the get_invoices partner and the create_invoice partner:
- active = NOT CustomerActivitySuspended (A; meaning undocumented); otherwise true. Beneficiary flags are ignored (beneficiaries are out of scope).
- addresses = one 'main' address built from Address (+Address2), ZipCode, Locality, CountryCode; address-level phone/email = null (company phone/email are returned at root: phone = ContactPhone, email = ContactEmail).
- is_company = true (Chift default; Horus does not store it, so disclose this as data loss).
- language = lowercase Horus Language for FR/NL/DE/EN/ES/PT; 'XX' → null.
- third_party_account = company SearchKey; account_number = CustomerConcentrationAccount (or SupplierConcentrationAccount for suppliers) resolved to the account SearchKey.
- **Write-side language fallback (everywhere):** a Chift language outside the Horus company enum → the folder language from folders.info (which may be 'XX').

## D10. partner_info in create_invoice
- partner_info.account_number has no description in the Chift spec. Treat it as the Horus company SearchKey (A) and add the [Chift] open question "What does partner_info.account_number mean: a third-party code or a ledger account?"
- **Proposal (depends on C8; recommended path = create the client/supplier first).** Look partner_info.account_number up exactly as sent, never sanitised or truncated (422 if it breaks the Horus search-key rules, H7): companies.list by ExternalReference (exact same-folder post-filter), then by SearchKey (exact, same folder). Reuse a match only if its normalised name (case and spacing ignored) equals account_name; a mismatch → 409 with the existing id (reuse with a warning is the alternative, C8). A missing role flag → 422 ('partner lacks the customer/supplier role; use client/supplier creation with force_merge'); companies.update (CompanyId + flag only, never "" values) only as a Chift-enabled opt-in. The same 422 applies when partner_id points to a company without the role. Otherwise create it with companies.new using create_client's required-field rules and SearchKey = account_number; defaulted fields (IsVatLiable=false, folder language/country) are reported as warnings if Chift supports them (C3), otherwise logged. Reuse on a code match is legitimate here because the key is the consumer's own code, whereas create_client derives its key from the name.
- create_client generates its own keys from the name (default: uppercase, accents removed, A–Z0–9, truncated to the Horus limit (H7), numeric suffix on collision; a prefix and sequence when the name gives too short a key; optional per-consumer scheme). This convention is a proposal for Chift (C8).

## D11. Verdict calibration (stated once in the report)
The definitions printed in section 2 ("How to read") are applied identically to every route, without exceptions by decree. Headline counts are computed by the generator, never written in prose.
- **Supported:** Horus endpoint(s) natively serve the route with deterministic mapping and cached reference lookups only; no extra live Horus calls per request beyond those needed to produce the response; no emulated filtering, paging or numbering; no loss of a capability clients typically rely on.
- **Supported with workaround:** feasible, but needs extra live calls per request (read-backs, joins, loops), emulated filters/paging/numbering, or loses a capability; the route works for the documented scope.
- **Not supported:** the route cannot be served from the documented API.
- **To confirm:** feasibility itself depends on an unanswered question.
- Consequences: Folders supported only while the folders.info country call is off by default (C4); analytic plans workaround (Low complexity: emulated paging on at most 8 rows, Free schemas hidden pending C9). create_misc_operation is **workaround** because of Horus constraints: amounts are stored in EUR only (foreign-currency operations converted at the supplied rate, original currency not kept), numbers must be numeric, and returning a Horus-generated number needs a read-back. The D12 duplicate pre-check is a connector safeguard and line_number (an ordering key) is preserved; neither is a reason for the verdict. create_ledger_account is workaround because the type cannot be written; its duplicate check and read-back are safeguards.

## D12. Posting status and duplicate checks (both write routes)
- **Posting mode (LD5, proposal, decision owner Chift C1):** chosen per connection at activation. *Review* (proposed default): every entry is pushed with Confirmed = false. *Direct*: Chift 'posted' → Confirmed = true, 'draft' → false. The response always reports the status actually stored (never 'posted' for an unconfirmed entry). Chift 'draft' = Horus unconfirmed: booked, visible in default list reads, not yet confirmed by the accountant, and deletable through the API for misc operations. Horus Confirmed means validated by the accountant and is not documented as equivalent to Chift 'posted'. Confirmed = true is accepted by the API; whether every licence or user may set it is undocumented (H21). This mode replaces the former per-consumer "always push unconfirmed" setting everywhere.
- **Numbering (proposal, C7):** unconfirmed entries without a number carry Number 0 (sales; purchases null). An invoice to be confirmed (direct mode) without invoice_number is pushed for review with Number 0 and returned as draft with invoice_number null (default); reject with 422 or max(DocumentNo)+1 (opt-in after H3, race risk) are alternatives. Purchases follow the same default until Horus answers (H3). Whether Horus numbers a confirmed invoice sent without a number is open (H3). invoice_number and operation_number are validated for round trip: non-numeric values, leading zeros and more than 15 digits are rejected with 422. operation_number is assumed to be the Horus entry Number; 0 is also rejected (Number 0 means "no number"); alternative: AutoGenerateNumber for confirmed operations with the client value in the line comment.
- **Duplicate pre-check:** whenever an invoice_number / operation_number is supplied, run POST /book-entries.list (FolderId, DaybookId, fiscal-year period, Filter.DocumentNo) before creating. Supplier invoices without a number: heuristic check on supplier (Filter.CompanyId) + Date + total, configurable per consumer (C6). On a timeout or 500, check before retrying (never blind-retry; Horus has no idempotency key). This is best-effort: an entry without a number has nothing to search on and is never retried automatically, and identical calls in flight are serialised by a connector-side lock (proposal).

## D13. Cross-folder guard on Id-only calls
Every Id-only call must verify the folder: companies.info → Data.Folder.Id, book-entries.info → Data.Folder.Id, daybooks.info → Data.Folder.Id = folder_id. Otherwise return 400. Analytics are resolved only from the folder-scoped cache (D8).
Exception for read-backs of an Id the connector has just created (invoice, misc operation, account, company): a mismatch is logged as an alert and the read-back data is not used, but the request is not failed, because the record exists. A failed read-back never leads to a re-create or an error; the response is built from the request values.

## D16. Invoice amounts and VAT as issued (create_invoice)
- **VAT as issued:** send OverrideTaxAmounts=true on every invoices.*.new call, so Horus books the VAT amounts of the issued invoice instead of recomputing base × rate (documented default: recalculated and adapted within 1 cent; behaviour beyond 1 cent undocumented, H22). regroup_lines, invoice_correction lines and invoices whose VAT was computed at invoice level depend on it. Plausibility check: reject with 422 a source line whose |tax_amount − untaxed_amount × tax_rate / 100| exceeds a tolerance; whether it is on by default, and the tolerance, are for Chift (C2, C19). Label D.
- **invoice_correction:** generated only for header/line differences within a rounding tolerance agreed with Chift (C19) and only when the consumer supplies invoice_correction; above it → 422 (A).
- **Sign:** credit notes are posted with Type=1 and positive amounts; a refund with a negative header total is multiplied by −1 as a whole document (header, lines, correction line); mixed-sign documents and invoices with a negative total are rejected (A, C5, H2).
- **Precision:** input amounts carry at most 2 decimals (more → 422 or rounding per C3); equality checks run in decimal arithmetic on cents (H22).
- Open questions: Horus amount validation (H22), Chift C2, C5, C19; Horus H2.
